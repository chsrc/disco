What is the 1× reference?

The 1× line is the rate at which the real DSC workloads demanded I/O, as measured on SWE-SRC (psrecord traces) or estimated where no direct measurement exists. Headroom = this storage's measured throughput ÷ that reference: >1× keeps up with margin; <1× means a real DSC would run slower than the SWE-SRC reference in that phase.

Which workload? The reference comes chiefly from the DSC-065 (DEEP_FIELD) imaging run — the heaviest workload with complete measurements — with one rate from the DSC-008 run and two from staging measurements (per-phase sources below). Other DSC families share these I/O patterns in different proportions, so the per-phase results stay valid for them; only the weighting of the score would change.

Caveat: SWE-SRC's own rates were partly storage-latency-bound (CPU was ~60% while reading; the same storage burst to 261–574 MB/s), so 1× means "the reference experience", not a fundamental requirement.

What is headroom?

Each row of the table carries a headroom badge (e.g. 5.5×). It answers: how many times over could this storage handle what the real workload needs for that step? It is the measured throughput divided by the 1× reference demand.

2× = twice as fast as needed; 1× = exactly enough; below 1× (red badge) = too slow for that step — the real workload would be held back by the storage there.

Headroom is shown per step because storage classes make different trade-offs — one can be fast for large sequential transfers but slow for small random ones, and a single average would hide that.

What is the score?

The headline score is the byte-weighted geometric mean of the per-phase headroom: score = exp(Σ wₚ · ln(headroomₚ)), where headroomₚ is the measured throughput ÷ the 1× reference demand, and wₚ is each phase's share of the workload's bytes.

Why a geometric mean: headroom values are ratios — a phase at 2× and a phase at 0.5× average out to 1× (neutral), and a phase below 1× pulls the score down no matter how fast the others are. Why byte-weighted: the phases are parts of one workload, so each counts according to how much data it moves — a 10× difference on a phase that carries 1% of the data counts for 1%, not as much as the phase that carries 40%.

Reading it: 1× = the workload's demand just met; above 1× = margin. Because the score is an average, one slow phase can be hidden by fast ones — check the per-phase table below for red "below 1×" badges: those mark the parts of the workload this storage cannot keep up with.

The CARTA phase is not part of the score. That phase imitates a person browsing images in a viewer, so it reads slowly on purpose — its throughput number reflects that chosen pace, not the storage's speed. For that phase, look at the p99 latency in the table instead: how long a single read takes (lower is better).

Where does everything come from?
whatwhere it comes from
the eight test phases reading the source code of all 12 active DSC workflows (public on the SRCNet GitLab). The tests replay the I/O patterns those workflows perform — without the astronomy software or its datasets.
file sizes and shapes in the tests the real datasets, as registered in the SRCNet Rucio data lake and listed on the DSCs data Hub page. Example: the DSC-065 dataset is 83 files totalling 3.2 TB, two of which hold 99% of the data — which is why the tests use two big files plus 81 small ones.
the 1× reference rates measured on SWE-SRC where possible: most come from the DSC-065 imaging run, one rate from the DSC-008 run, one from Rucio transfer measurements, and four are estimates. The per-phase breakdown with links is in the "What is the 1× reference?" panel at the top.
how much each phase counts in the score byte shares measured in the same DSC-065 run: it read 1.04 TB and wrote 808 GB over its 4.6 hours. The percentages shown next to each phase name are these shares; together the eight phases cover 89% of the run's I/O (the rest is in patterns not run in the score scenario).
the 4.6 h compute budget the wall-clock time of that same DSC-065 run.
throughput, IOPS and latency in this report no reference — measured on this storage by the benchmark itself. They are properties of the storage and stay the same whichever DSC you care about.

If a different DSC family mattered more (pulsar timing, HI cubes…), the per-phase measurements stay valid; the weights and reference rates would be re-derived from that family's runs. Only the DSC-065 tables exist today.
